# 状态可信与安全：批次 A 设计

## 目标

修复三类“客户端看到的结果与持久化状态不一致”问题，使普通行动与战斗的关键数值只由服务端权威结算，并在成功响应中返回已提交的最新状态。

范围：

1. 普通行动经验原子结算。
2. 战斗忽略客户端传入的角色属性。
3. 战斗胜利的金币、经验与物品掉落原子持久化。

不在本批次范围：遗留 API 鉴权、资源并发保护、突破事务化、会话改造；这些属于后续批次 B。

## 设计

### 1. 普通行动经验

`executeAction` 计算 `expGained` 后，在同一数据库事务中以原子增量更新 `cultivationExp` 与 `totalExp`。后续突破资格必须基于提交后的角色状态计算。接口返回的 `cultivator` 是事务提交后重新读取或 update 返回的权威快照，前端不得依据客户端本地加法猜测数值。

错误时事务整体回滚，不写行动记录、不写经验、不返回虚假的经验获得结果。

### 2. 战斗角色属性权威

`/api/combat` 从数据库读取当前角色，并从其持久化 `attributes` 归一化为战斗引擎输入。请求体中的 `attributes` 不参与战斗计算；为保持请求兼容可以接受但必须忽略。敌人参数继续由现有服务端规则验证或生成。

响应包含实际用于战斗的结算结果与提交后的角色快照，不暴露内部数据库字段。

### 3. 战斗奖励与库存

战斗胜利时，将以下变化放进同一个事务：

- 角色金币增量；
- 角色经验增量；
- 掉落物与既有 `inventory` 合并后写回；
- 必要的战斗事件/记录。

任一步失败，金币、经验、库存和事件均不变。事务成功后返回最新角色快照和已持久化奖励结果。掉落数量按现有库存合并规则处理，避免相同 itemId 产生不必要的重复槽位。

### 4. 前端同步契约

本批次涉及的服务端状态变更接口必须返回最新 `cultivator`。store 收到 `cultivator` 后以服务端快照整体更新，仪表盘的修为、金币、背包和突破资格不做乐观猜测。

## 测试

- 行动经验：验证经验与总经验真实增加、响应与持久化状态一致、失败时不部分写入。
- 战斗属性：请求伪造高属性，验证战斗引擎使用数据库属性。
- 战斗奖励：验证金币、经验和物品写入；模拟库存/写入失败时验证事务回滚。
- 回归：既有战斗失败惩罚、行动体力扣减和 UI 状态同步测试继续通过。

## 验收标准

1. 普通行动后刷新页面，经验与响应一致且可用于正确判断突破。
2. 伪造客户端属性不改变战斗输入。
3. 战斗胜利后刷新页面，金币、经验和掉落物仍存在。
4. 任意奖励持久化失败不会留下部分金币、经验或物品。
5. 所有定向测试、全量测试和 TypeScript 检查通过。
